# 受管 QQ 配置与登录

快速配置第三步提供「配置并登录 QQ」。自动创建连接适用于已准备的 NapCat 4.18.41 Windows Node 组件；手工 Shell 沿用现有连接配置，外部 OneBot 在原服务登录。

日常登录可直接点击「工作总览 → 服务连接 → QQ 登录」，或「连接与运行」顶部的「QQ 登录」。已有本机手工部署也可在此查看二维码、刷新和确认登录，沿用 `napcat/node-runtime/config/webui.json` 的本机端口与认证，不改写 OneBot 或 WebUI 配置；尚未运行时点击「启动现有 QQ」。外部 OneBot 须在原服务中登录。

点击「自动配置并启动 QQ」后，程序创建仅绑定 `127.0.0.1` 的 HTTP、正向 WebSocket 和 WebUI 端口，分别检查端口可用性，生成随机连接令牌。OneBot 默认使用消息段数组、关闭 CORS 和其它网络适配器。连接结果填入草稿，检查并保存后才用于桥接；该操作不启动模型或发送 QQ 消息。

已有手工配置不会覆盖。受管配置发生改变时先报告冲突，不强行重置。准备过程记录固定文件的摘要；中断后只能清理内容仍与本次准备一致的文件，检测到新修改时保留全部文件供核对。创建配置不代表服务一定启动成功，端口检查与实际监听之间仍有竞争窗口，后续状态检查会解释连接失败。

登录窗口显示二维码、已扫码待确认、初始化、在线或需要处理等阶段；二维码只允许官方 QQ HTTPS 地址。状态、账号和 OneBot 配置分别验证，不把进程存在当作已登录。刷新二维码由用户主动触发；额外验证按官方流程处理，不绕过验证。关闭窗口后 QQ 继续运行，在工作台点击停止才结束受管进程。

QQ 原生库的资料目录通过实例适配器指向当前数据目录的 `napcat/qq-profile/`。适配器只在加载固定组件的 `wrapper.node` 时包装公开入口，不修改二进制、系统 QQ 路径配置或其它模块。原生入口结构不兼容时拒绝继续启动。NapCat 的配置和工作文件仍位于 `napcat/node-runtime/`，组件更新不会重新选择系统 QQ 账号目录。

本机启动器启用 NapCat 主进程管理登录 Worker，以便登录失效时重建登录服务。受管模式通过继承的 `--import` 在每个新建 Worker 加载原生库前安装上述目录隔离；重建后仍使用同一实例的资料、配置和登录材料。缺少绝对实例路径时拒绝启动；不通过清空登录数据恢复服务。手工 Shell 模式保留原有资料位置，外部 OneBot 不由本程序重启。

更新启动脚本后须在工作台点击「重新启动」，仅「重连模型」不会更新 QQ 进程。登录凭据失效或要求额外验证时，仍须在登录窗口或本机 WebUI 按官方流程重新扫码和验证。

WebUI 凭据只在管理进程内存中缓存，支持文件令牌轮换与有限的认证重试；不会把上游敏感错误原文转发到工作台。主工作日志隐藏上游输出的 WebUI 令牌、登录 URL 和终端二维码。NapCat 自己仍可能在其缓存和日志中保存登录二维码、账号材料，应保护整个数据目录，默认诊断与分发不得包含这些目录。不能把工作台日志脱敏描述为上游从不落盘。

登录适配使用固定版本的[QQ 登录路由](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-webui-backend/src/router/QQLogin.ts)和[认证路由](https://github.com/NapNeko/NapCatQQ/blob/v4.18.41/packages/napcat-webui-backend/src/router/auth.ts)，默认网络配置格式参照[官方说明](https://napneko.github.io/config/basic)。实现为独立适配，尚不承诺其它 NapCat 版本兼容。

登录、鉴权、端口隔离、中断恢复和原生窗口已通过受控验证；真实账号仍可能要求额外验证，首次使用请按官方流程操作。
