# 云服务器部署与本地远程控制台方案

更新日期：2026-10-31。本文件保留方案与实施进展记录。范围：机器人及 QQ、模型运行组件部署在 Linux 云服务器持续运行；Windows 桌面控制台保留在本地，通过远程连接管理；现有聊天、权限、记忆、任务、媒体和维护功能保持不变。

## 一、目标与硬性边界

| 项目 | 约定 |
| --- | --- |
| 运行位置 | 机器人桥接、DSH 模型链路、NapCat/QQ、数据库与媒体全部在 Linux 服务器 |
| 部署顺序 | 当前没有云服务器：先在本地 Ubuntu 24.04 虚拟机完成部署与验收，再购买服务器复用同一产物与步骤 |
| 服务器区域 | 计划部署在中国大陆，降低 QQ 登录与收发延迟；购买前再确认服务商限制 |
| QQ 账号 | 使用现有主账号；切换前先停掉 Windows 实例，避免两端同时在线 |
| 控制位置 | 现有 WPF 桌面控制台继续作为主要管理界面，运行在本地 Windows |
| 控制台模式 | 保留双模式：同一控制台可直连本机，也可远程连接服务器，按连接配置切换 |
| 生命周期 | 关闭控制台、退出 SSH 或网络中断后，服务器上的机器人继续运行 |
| 功能范围 | 保持现有功能集合与行为，不因部署方式删减或改写业务逻辑 |
| 网络暴露 | 公网只开 SSH；管理、OneBot、QQ WebUI 一律只监听回环地址 |
| 不替代项 | 网页控制台是既有能力，可保留，但不作为本次需求的控制台 |
| 不承诺项 | 本方案不把 Windows 已有验证结果当作 Linux 验收；正式签名、干净系统、真实账号观察仍按原门槛执行 |

## 二、现有资产与差距

可直接复用的部分：

- `scripts/runtime-service.mjs`：管理核心，动作集合为 `maintenance / qq-login / components / onboarding / model / qzone-check / knowledge / social / memory / settings-status / load / settings / env / runtime / connection / persona / diagnose / start / restart / restartBridge / stop / quit`，请求为单行 JSON，事件为单行 JSON，4 MiB 行上限，命令串行排队。
- `desktop/host.mjs`：同一协议的 stdio 宿主，桌面端通过 stdin/stdout 收发。
- `desktop/App.cs`：`Send()` 写一行 JSON，200 ms 轮询事件队列，已具备断线提示与恢复提示的界面处理。
- `scripts/app-paths.mjs`：已按平台区分数据目录（Windows `LOCALAPPDATA`，Linux `XDG_DATA_HOME`/`~/.local/share`），支持 `--data-dir` 与 `--portable`。
- `server/app.mjs`：网页控制台已用 `createRuntimeService` 管理实例，说明"管理服务 + 事件发布"可脱离桌面运行。
- 维护、备份、诊断、媒体清理、组件安装、升级回退都已有服务端实现，桌面只是发起端。

必须补齐的差距：

| 差距 | 现状 | 影响 |
| --- | --- | --- |
| 进程生命周期 | `host.mjs` 在 stdin 关闭时调用 `service.close()`，其中会 `stop()` 停止机器人 | 直接 SSH 转发会让"关控制台"等于"停机器人" |
| 单实例管理 | `createRuntimeService` 持有运行管理实例锁 | 同一服务器只能有一个管理进程，桌面与网页不能各起一个 |
| Linux 组件 | `components/catalog.json` 仅 `win32-x64`；Node、DSH、NapCat 对应条目与摘要只有 Windows | 不能在 Linux 上准备受管运行环境 |
| 进程守护 | `scripts/process-guard.mjs` 在 Windows 用 Job Object；非 Windows 退化为进程组 | Linux 需要 systemd/cgroup 级别的回收与开机恢复 |
| 凭据存储 | Windows 使用 DPAPI 引用 | Linux 无 DPAPI，需要新的凭据提供者，且旧凭据无法直接迁移 |
| 桌面入口 | 安装、升级、回退、修复、卸载面板直接操作本机路径与注册表 | 远程模式下这些入口要么隐藏，要么改为服务器端操作 |
| 文件语义 | 备份、诊断、组件导入、日志与记忆目录使用本地文件对话框和本地路径 | 远程模式需要"服务器路径 + 本地下载/上传"的转换 |
| 平台验收 | Linux 首轮 510 通过/1 失败/9 跳过，修复后仅专项复测 | 无 Linux 全量通过记录，虚拟机目录也已不存在 |

## 三、架构选型

### 方案一：SSH 透明转发现有 NDJSON

桌面端把 `node desktop/host.mjs` 替换为 `ssh 服务器 node <程序目录>/desktop/host.mjs`，协议不变。

- 优点：桌面改动最小，功能事件流原样复用。
- 缺点：`host.mjs` 拥有管理锁与子进程生命周期，连接断开即触发 `close()` 并停止机器人；重连会重新接管，操作队列丢失；无法同时支持网页控制台。
- 结论：不单独采用，仅作为连接层实现手段。

### 方案二：桌面改为网页管理 API 的客户端

复用 `server/app.mjs` 的 HTTP/鉴权/SSE，把 WPF 改为 HTTP 客户端。

- 优点：服务端已有鉴权、任务与事件发布；天然支持断线重连与多客户端。
- 缺点：现有桌面协议是一问一答加事件流，改造成本高；二维码、组件进度、取消语义都要重新映射；网页与桌面容易产生功能分叉。
- 结论：不采用为主路径。

### 方案三（推荐）：服务器守护进程 + SSH 连接转接

把管理核心常驻化，桌面通过 SSH 启动一个只做协议转发的轻量进程：

```
本地 WPF ──stdio NDJSON──> ssh ──> remote-host.mjs ──unix socket──> whaled（唯一管理进程）
                                                                     ├─ bridge（模型链路）
                                                                     ├─ DSH
                                                                     └─ NapCat / QQ
```

- `whaled` 由 systemd 托管，持有实例锁与子进程，负责启停、恢复、维护、备份与开机自启；与控制台连接无关。
- `remote-host.mjs` 只是一条连接：把 stdin 的行转给 `whaled`，把事件写回 stdout；断开时**不**停止服务。
- 桌面仍使用现有 `Send()`/事件模型，只把"启动本地 node 子进程"改成"启动 ssh 子进程"，并新增连接配置；本机模式保持原有启动方式，两种模式共用同一套界面与事件处理。
- 网页控制台改为连接同一个 `whaled`（或暂缓并行支持），避免两个管理进程争锁。
- 关闭控制台 = 断开一条连接；停止机器人 = 显式 `stop`/`quit` 动作，语义与现在一致。

## 四、服务器侧设计

### 4.1 目录与服务

首版在本地 Ubuntu 24.04 x64 虚拟机落地，规格按下表执行；虚拟机验收通过后再购买云服务器，部署步骤与产物不变，届时只替换主机与凭据。

| 内容 | 位置 |
| --- | --- |
| 程序 | `/opt/whaleworkbench/current`（版本目录 + `current` 链接） |
| 数据 | `/var/lib/whaleworkbench`（或安装时指定的 `--data-dir`），权限 0700，属主为服务账户 |
| 固定运行时 | `/opt/whaleworkbench/runtime`（Linux x64 Node，摘要校验） |
| 组件 | 数据目录下受管组件区，保持与 Windows 同一套摘要校验 |
| 服务 | `whaled.service`，`Type=simple`，`Restart=on-failure`，`KillMode=control-group` |
| 日志 | journald；应用内日志仍写数据目录，脱敏规则复用 |

- 安装/升级：沿用现有签名清单与版本目录切换逻辑，Linux 侧新增安装脚本与 systemd 单元，不引入第二套信任模型。`scripts/whaled-install.mjs` 写入 systemd 单元（支持 `--service` 指定单元名，便于隔离验收）；`scripts/whaled-upgrade.mjs` 校验签名后复制到 `releases/<uuid>`、原子切换 `current`、重启服务并执行启动检查，检查或启动失败自动切回上一版；`--rollback` 手动回退，`--recover` 处理中断记录，`--dry-run` 只校验不切换。
- 升级只更换程序文件，不改写数据目录；数据库、配置、凭据与备份仍由桌面维护入口处理。回退只切回程序版本，不用旧快照覆盖数据。
- 退出 SSH、关闭控制台、重启控制台：服务不受影响；服务器重启后由 systemd 恢复。
- 维护模式的"先停后操作"语义保留：备份、恢复、媒体清理期间拒绝普通启动。

### 4.2 Linux 运行组件

1. 固定 Linux x64 的 Node 版本，来源、摘要、许可证入目录表。
2. DSH 使用与 Windows 相同的 npm 版本与锁定摘要。
3. NapCat：已确定在服务器内运行并扫码登录，使用现有主账号。阶段 1 先验证官方 Linux 发行方式与无桌面运行要求（依赖、权限、扫码链路）；每次登录前先停掉 Windows 实例，避免两台设备同时在线。验证不通过时暂停并说明具体阻塞，不自行改用外部 OneBot，也不用 Windows 组件冒充。
4. 组件安装仍需用户确认、进度、取消与失败保留旧版本。
5. 补充 Linux 媒体清理、备份、恢复、诊断路径，与 Windows 行为对齐。

### 4.3 凭据与账号

- 新增凭据提供者抽象：Windows 保持 DPAPI；Linux 首版使用 0600 权限的密钥文件（可结合 systemd credentials），不使用明文进入日志或进程参数。
- Windows 上的 DPAPI 凭据**不能**直接迁移到 Linux：模型密钥、QQ 相关凭据需要在服务器上重新录入。
- QQ 登录态不保证跨平台迁移，首次部署按新登录处理，需要扫码；这是验收项，不是缺陷。
- QQ 登录态会被异地登录、IP 变化或长时间离线强制失效，机器人无法自行恢复；请保持设备常开、网络固定，看到掉线提示时在「QQ 登录」窗口重新扫码。
- 现有 `.wwbackup` 加密备份可在知道口令时跨平台恢复数据，但其中由 DPAPI 保护的引用在 Linux 上不可用，需重新录入对应密钥。

### 4.4 数据迁移（已确定执行）

1. 先停止 Windows 侧机器人并确认不再写入，再在现有维护入口生成加密备份，校验通过后复制到服务器；不直接拷贝运行中的数据库文件。
2. 服务器保持空实例即可迁移；跨设备或跨数据目录使用「从其它设备迁移」，仍校验数据布局、配置相对路径与文件摘要，并在切换前为服务器当前数据创建加密恢复点；失败时不覆盖已有数据。原实例恢复入口保持原有路径限制。
3. 恢复完成后抽样核对会话数、群上下文、长期记忆、提醒与配置项；记录实际数量，不只检查"能启动"。
4. 迁移完成后 Windows 实例转为只读保留，禁止两端同时处理消息；确认稳定后再决定旧实例的去留。
5. 模型密钥、QQ 相关凭据重新录入；QQ 首次登录扫码。上述两项不计入"迁移失败"。

## 五、本地控制台改造

1. 双模式：连接配置区分"本机"和"远程"；本机沿用现有启动方式，远程走 SSH。当前连接对象在界面上明确显示，切换连接不合并两边数据，远程配置不影响本地自动启动。
2. 新增"连接配置"：主机、端口、用户名、私钥路径、服务器程序路径、数据目录；配置保存在本地，私钥不复制进仓库。
3. 主机身份固定：首次连接展示并保存服务器 SSH 主机密钥指纹，后续变更必须显式确认，禁止静默接受。
4. 连接状态：未连接/连接中/已连接/连接中断/服务器未运行；现有"控制进程已退出"文案改为区分本地 ssh 失败与远端服务异常。
5. 断线处理：自动重连并重新拉取状态；重连期间禁用会改变服务端状态的按钮，避免重复提交；未完成操作需在服务端继续或明确标记失败，不能假装成功。
6. 生命周期语义：远程连接关闭窗口仅断开连接（机器人继续运行）；本机模式保持现有行为；远程模式托盘"退出并停止机器人"只停止服务器上的机器人并结束控制台，`whaled` 守护进程保持运行，之后可直接重新连接；新增"断开连接"与"退出控制台"的区分保持。
7. 远程模式下隐藏或改写 Windows 专属入口：安装/升级/回退/修复/卸载改为服务器端升级操作；开始菜单、注册表、快捷方式相关界面不出现。
8. 文件操作改为"服务器执行 + 本地传输"：
   - 备份：服务端在暂存目录生成 `.wwbackup`，桌面通过 SFTP 下载后可删除暂存。
   - 恢复：桌面先上传到服务器暂存目录，再发起恢复；路径与实例校验规则不变。
   - 组件导入：本地上传后传服务器路径。
   - 诊断导出、日志导出：服务端生成后下载。
   - 记忆/工作区/媒体文件：提供远程浏览与下载，不伪装成本地资源管理器；"打开目录"按钮在远程模式改为下载或只读列表。
9. 二维码与登录：沿用现有 `qq-login` 事件流，确认二维码图片在 SSH 链路上以现有编码方式完整传输。

## 六、阶段与验收

### 阶段 0：环境与基线

- 云服务器尚未购买，本阶段使用本地 Ubuntu 24.04 x64 虚拟机（2 核/3 GiB/20 GiB，SSH 密钥登录），规格与后续购买目标一致。
- 新建 `codex/linux-remote-console` 分支；在该环境跑 Linux 全量回归，补齐首轮 510/1/9 之后未复跑的全量记录。
- 验收：Linux 全量结果、失败项修复与复测记录齐全；不以 Windows 结果代替。

### 阶段 1：Linux 运行核心

- 固定组件目录（Node/DSH/NapCat）、Linux 路径、权限、进程组与停止恢复、媒体清理与诊断。
- 先完成 NapCat Linux 可行性验证；不通过时暂停并给出阻塞原因与可选方案，不自行降级接入方式。
- 验收：空实例能准备组件、启动/停止/异常恢复；维护期间拒绝普通启动；组件摘要可核对。

### 阶段 2：守护进程与系统服务

- `whaled` 常驻、单实例锁、unix socket 或回环管理接口、systemd 单元、开机恢复、日志。
- 管理接口只对本地回环/本机用户开放；断开所有客户端不停止机器人。
- 验收：退出 SSH、关闭控制台、重启服务后状态与队列行为符合定义；服务重启后机器人按策略恢复。

### 阶段 3：桌面远程连接

- 连接配置、主机密钥固定、ssh 子进程转发、连接状态、重连、取消、超时、按钮禁用。
- 验收：断网、服务器重启、重复连接、两个控制台同时连接、连接期间取消操作，均有明确且一致的结果。

### 阶段 4：远程文件与功能对齐

- 备份上传/下载、诊断导出、组件导入、日志与媒体访问、记忆与工作区浏览。
- 验收：按现有功能清单逐项核对，宁可标注"暂不支持"并说明替代路径，也不静默失效。

### 阶段 5：端到端验收与交付

- 在虚拟机上完成从空实例到安装、扫码就绪、真实私聊、重启恢复、升级失败处理、备份恢复的完整闭环；留存环境、组件版本、代码版本与通过/失败记录。
- 验收：文档、失败样本与未验证项清单齐全，再形成部署分支交付检查点。
- 虚拟机验收通过后，在中国大陆购买云服务器并按同一产物与步骤部署；该步骤属于实际交付操作，不另开代码分支，也不把虚拟机结果当作公网环境验收。

## 七、风险与未决项

| 风险 | 处理方向 |
| --- | --- |
| NapCat Linux 无桌面运行能力未确认 | 阶段 1 先做可行性验证；不满足时暂停汇报，由用户决定是否接受替代接入 |
| QQ 新环境登录可能触发安全验证 | 使用现有主账号：先停 Windows 实例、提前准备手机确认；流程保留人工扫码，验收窗口内不并行运行 |
| 凭据无法跨平台迁移 | 部署文档写明需重新录入；备份恢复说明区分数据与凭据 |
| 多客户端与单实例锁冲突 | 统一由 `whaled` 持有锁；网页与桌面都作为连接方 |
| 事件流在弱网下丢行/重复 | 连接建立时全量拉取状态；事件带序号与重放点，重连后重新同步 |
| 远程文件操作误删服务器数据 | 上传/下载分离暂存目录；删除类操作保持确认与白名单路径 |
| 升级/回退在 Linux 上未演练 | 已在虚拟机用内部验证密钥完成签名安装、正常升级、检查失败与启动失败自动回退、手动回退、中断恢复与 dry-run；正式签名和公网环境仍按原门槛单独验收 |
| 云服务器尚未购买，公网 IP、带宽与 SSH 端口未定 | 先在虚拟机验收；购买后按同一产物部署，公网开放与主机密钥在部署时确认 |
| 迁移后两端数据不一致 | 迁移完成即停用 Windows 侧写入；抽样核对记录数，保留迁移前备份 |

## 八、明确不在本方案内

- 不把管理端口、OneBot 或 QQ WebUI 暴露到公网，不引入公网 HTTPS 控制台方案。
- 不改动聊天、权限、记忆、任务、媒体等业务行为，不以部署改造顺带重构业务。
- 不用网页控制台替代本地桌面控制台要求。
